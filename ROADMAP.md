# MaintainSoft — Engineering Roadmap

> Generated by an audit of the live repo on 2026-09-22. This file is self-contained: an
> agentic coding assistant should be able to pick up this project using only this
> document plus the source tree, without prior conversation context.
> **Rule for any agent working from this file:** re-read the actual source before editing
> it — this document describes state as of the audit date and may drift. Verify a claim
> against the file before trusting it.

## 0. Project Summary

MaintainSoft is an intentionally over-engineered Spring Boot learning project: a
maintenance-management platform (machines, repairs, spares, technicians, departments,
users) built for exposure to production-grade Spring Boot patterns, not for real load.
Favor doing things the "proper" production way over the shortcut, as long as it stays
inside the stack already chosen below.

- Package root: `com.maintainsoft`
- Layout: `controller/ dto/ entity/ enums/ exception/ repository/ security/ service/`
- Server port: `6969`, base API path: `/api/v1`

## 1. Locked Design Decisions — do not violate these

1. Two system roles only: `MANAGER` and `SUPERVISOR`. ADMIN and MANAGER are the same
   role (do not add a separate ADMIN role).
2. `TECHNICIAN` is a lightweight domain entity — **not** a system user, has no login.
3. Auth is RSA-signed JWT, stateless, via `spring-boot-starter-oauth2-resource-server`
   as resource server + a hand-rolled issuer (`SecurityConfig` builds `JwtEncoder`/
   `JwtDecoder` from `classpath:private.key` / `classpath:public.key`).
4. `RepairUpdate` is an **append-only** audit log for a repair's status history.
5. `RepairSpare` is the `Repair`↔`Spare` join entity and carries `used_quantity`.
6. Soft deletes on history-bearing entities (`User`, `Department`, `Machine`, `Spare`)
   via `@SQLDelete` + `@SQLRestriction("deleted = false")` — follow the pattern already
   in `entity/User.java`.
7. Machine status transitions should be event-driven (not yet implemented — see Phase 5).
8. Flyway owns schema migrations. Jasypt encrypts sensitive properties. JPA auditing
   (`@CreatedBy`/`@CreatedDate`/etc., via `BaseEntity`) stamps every entity.
9. **No public self-registration.** First `MANAGER` is seeded (see
   `security/DatabaseInitializer.java`). All subsequent users are created by an
   authenticated `MANAGER` via `POST /users`. This is currently violated — see P0-2.

## 2. Stack Reference

- Spring Boot `4.0.6`, Java `26`, Maven.
- Key deps already in `pom.xml`: `spring-boot-starter-data-jpa`, `spring-boot-starter-webmvc`,
  `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server`,
  `postgresql`, `lombok`, `jasypt-spring-boot-starter` (4.0.4), `springdoc-openapi-starter-webmvc-ui`
  (3.0.3), `resilience4j-ratelimiter` (2.4.0, **not yet used anywhere in source** — confirm
  need before wiring it in), `spring-boot-starter-flyway` + `flyway-database-postgresql`,
  `spring-boot-starter-actuator`.
- DB: Postgres at `msi.leo-blenny.ts.net` (Tailscale-only homelab host — see the
  OCI Lab project notes if this agent has access to them).
- Conventions already established — follow them for all new code:
  - DTOs are Java `record`s in `dto/`.
  - Services use Lombok constructor injection (`@RequiredArgsConstructor` or
    `@AllArgsConstructor`), never field injection.
  - Custom exceptions live in `exception/`, one class per case, all handled centrally in
    `exception/GlobalExceptionHandler.java` via `@RestControllerAdvice`.
  - Entities extend `entity/BaseEntity.java` (UUIDv7 id, audit columns, `@Version`).
  - Every layer gets a test: see `AuthServiceTest`, `DepartmentServiceTest`,
    `JwtServiceTest`, `DtoAndEnumTest`, `EntityTest`, `GlobalExceptionHandlerTest`,
    `*ControllerTest` for the existing pattern — new features must match this coverage
    shape (entity + dto + service + controller + relevant exception tests).

## 3. Current Implementation Inventory (as of audit)

**Entities (all present, schema confirmed via generated DDL):** `BaseEntity`,
`Department`, `Machine`, `Repair`, `RepairSpare`, `RepairUpdate`, `Spare`, `Technician`,
`User`.

**Implemented endpoints:**
- `POST /api/v1/auth/register` — public, creates a `SUPERVISOR` — **must be removed/locked
  down, see P0-2.**
- `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh` — functional.
- `GET/POST/PATCH/DELETE /api/v1/department(s)` — functional, no role restriction (P0-3).
- `GET /api/v1/health` — authenticated echo of principal name.

**Not implemented yet:** any controller/service for `Machine`, `Repair`, `Spare`,
`RepairUpdate`, `RepairSpare`; `POST /users` (the design-mandated user-creation path);
method-level authorization; DB-backed refresh tokens; machine status event handling.

## 4. P0 — Fix Before Any New Feature Work

These block correctness or are live security gaps. Do them first, in any order, but all
before starting Phase 1.

### P0-1: Schema management is fully disabled
`application.properties` currently has `spring.flyway.enabled=false` and
`spring.jpa.hibernate.ddl-auto=none` — a fresh DB will have zero tables.
`src/main/resources/db/migration/V1__init_schema.sql` also contains the same
`CREATE TABLE ...` block **duplicated four times** (an artifact of repeated
Hibernate schema-export runs appending instead of overwriting) — Flyway will fail on
duplicate-table errors if pointed at this file as-is. There is also a stray
`V1_initDB.sql` with invalid Flyway naming (single underscore) that collides on
version "1".
- [ ] Delete `V1_initDB.sql`.
- [ ] Rewrite `V1__init_schema.sql` to contain each `CREATE TABLE`/`CREATE INDEX`/
      `ALTER TABLE ... ADD CONSTRAINT` statement exactly once (dedupe the 4x repeat).
- [ ] Set `spring.flyway.enabled=true`.
- [ ] Set `spring.jpa.hibernate.ddl-auto=validate` (never `update`/`create` once Flyway owns
      the schema — this is a locked design decision).
- [ ] Remove or scope the `schema-generation.scripts.create-target` properties so future
      Hibernate exports don't silently corrupt the migration file again — regenerate to a
      scratch path outside `db/migration` if that workflow is still wanted.
- [ ] Verify: app boots clean against an empty Postgres DB and `flyway_schema_history`
      shows one applied migration.

### P0-2: Public self-registration is live and violates the locked design
`SecurityConfig` permits all of `/api/v1/auth/**`, and `AuthController.register()` →
`AuthService.register()` lets anyone create a `SUPERVISOR` account with a
client-supplied `department` UUID, no auth required.
- [ ] Remove `POST /api/v1/auth/register` from `SecurityConfig`'s `permitAll()` list (or
      delete the endpoint entirely — design says creation only happens via `POST /users`).
- [ ] Implement `POST /users` per the locked design: `MANAGER`-only, creates a user with a
      role the manager specifies (or defaults to `SUPERVISOR`), reusing the duplicate-email
      check and password-encoding logic already in `AuthService.register()`.
- [ ] Verify: an unauthenticated `POST /api/v1/auth/register` (or `/users`) call returns
      401/403; a `MANAGER`-authenticated `POST /users` call succeeds; a `SUPERVISOR`-
      authenticated call is rejected.

### P0-3: No method/role-level authorization anywhere
`SecurityConfig` only has `anyRequest().authenticated()` — no `@EnableMethodSecurity`,
no `@PreAuthorize`. Any authenticated user, including a `SUPERVISOR`, can currently hit
every `DepartmentController` write endpoint.
- [ ] Add `@EnableMethodSecurity` to `SecurityConfig`.
- [ ] Define and document a role matrix (which endpoints are `MANAGER`-only vs. any
      authenticated user) before annotating — department create/update/delete and the new
      `POST /users` are strong `MANAGER`-only candidates; `GET` listing endpoints can likely
      stay open to any authenticated role.
- [ ] Apply `@PreAuthorize("hasRole('MANAGER')")` (or equivalent) to the endpoints the
      matrix marks as restricted. Note `UserDetailServiceImpl` already maps
      `user.getRole().name()` into `.roles(...)`, so `hasRole('MANAGER')` matches directly.
- [ ] Add controller tests asserting 403 for the wrong role and 200 for the right one, for
      every newly-restricted endpoint.

### P0-4: Refresh tokens are unrevocable
`JwtService.validateRefreshToken` only decodes and checks a `type` claim — nothing is
persisted, so there is no logout, no rotation, no way to invalidate a leaked refresh
token before its 7-day expiry.
- [ ] Add a `RefreshToken` entity (extends `BaseEntity` or a lighter base — id, `userId`,
      a hash of the token (or its `jti`), `expiresAt`, `revoked` boolean).
- [ ] On `AuthService.login`/`refresh`, persist the issued refresh token; on `refresh`,
      look it up, reject if revoked/expired/not-found, then **rotate**: mark the old row
      revoked and persist the newly issued one (do not just re-issue against the same row).
- [ ] Add `POST /api/v1/auth/logout` that revokes the presented refresh token.
- [ ] Add a scheduled or on-read cleanup strategy for expired rows (simple `@Scheduled`
      delete is fine for this project's scale).
- [ ] Verify: refresh after logout fails; refresh twice in a row with the same token fails
      the second time (rotation enforced).

### P0-5: Secrets are not protected from version control
`application.properties` as the `ENC(...)` values it's meant to protect, which defeats
the point of encrypting them. `private.key` / `public.key` (the JWT RSA signing keypair)
live under `src/main/resources`. None of `application.properties`, `private.key`, or
`public.key` are excluded in `.gitignore`.
      `JASYPT_ENCRYPTOR_PASSWORD` environment variable or `-D` system property instead.
- [ ] Confirm (`git log --all -- src/main/resources/private.key` or equivalent) whether the
      RSA private key or plaintext secrets have ever been committed. If yes: rotate the RSA
      keypair and any encrypted credentials, and scrub history (`git filter-repo` or BFG) —
      don't just add `.gitignore` going forward, that alone does not remove existing history.
- [ ] Add `private.key`, `public.key`, and any local-only `application-*.properties` to
      `.gitignore`. Keep only an `application.properties.example` with placeholder values
      committed, if a template is wanted.

### P0-6: Department create has a TOCTOU race
`DepartmentService.createDepartment` checks-then-inserts on `deptName` — under
concurrent requests, both can pass the "empty" check, the DB's unique constraint on
`dept_name` then throws a raw `DataIntegrityViolationException` that isn't mapped in
`GlobalExceptionHandler`, so it falls through to the generic 500 handler instead of a
clean 409.
- [ ] Either rely purely on the DB constraint (attempt the insert, catch
      `DataIntegrityViolationException`, translate to `DuplicateDepartmentException`) or
      keep the pre-check but make the failure path consistent — pick one, don't keep both
      half-implemented.
- [ ] Add a test that simulates the duplicate-insert path and asserts a 409, not a 500.

### P0-7: `updateDepartment` matches by name, not by id, despite its parameter name
`DepartmentService.updateDepartment(DepartmentRequest departmentID)` looks up the
department by `deptName`, so the department's name can never actually be changed through
this endpoint, and the parameter naming is misleading.
- [ ] Decide the intended contract: update-by-id (accept a `UUID`, allow renaming) is more
      standard for a PATCH endpoint — recommended unless there's a reason to keep
      name-as-key.
- [ ] Rename the parameter/DTO field to match whatever key is chosen, update
      `DepartmentController` and tests accordingly.

### P0-8: `DESIGN.md` is missing from the repo root
Prior project notes treat `DESIGN.md` at the repo root as the authoritative spec, but it
is not present in the current tree.
- [ ] Confirm with the project owner whether it was renamed, moved, or never committed.
- [ ] If it doesn't exist, this `ROADMAP.md` plus §1 above should be treated as the
      interim source of truth until one is recovered or written.

## 5. Phased Build Plan (after all P0 items are closed)

Each phase should end with `mvn test` green and new tests matching the coverage shape in
§2. Do not start a phase until the previous one's acceptance criteria are met.

### Phase 1 — Authorization hardening (folds in P0-2/P0-3 if not already done)
- Role matrix finalized and documented (in this file or a `docs/authorization.md`).
- `POST /users` implemented, `MANAGER`-only.
- All existing and new mutating endpoints annotated per the matrix.
- **Acceptance:** controller tests cover 200 (correct role) and 403 (wrong role) for every
  mutating endpoint.

### Phase 2 — Flyway + clean migrations (folds in P0-1 if not already done)
- Single, deduplicated `V1__init_schema.sql`, Flyway enabled, `ddl-auto=validate`.
- **Acceptance:** `mvn spring-boot:run` against an empty DB succeeds; `flyway:info` shows
  a clean, single-version history.

### Phase 3 — Machine and Spare service/controller layers
- `MachineRepository`/`SpareRepository` already exist — add `MachineService`,
  `SpareService`, and corresponding controllers under `/api/v1/machines`, `/api/v1/spares`.
- CRUD + list, following the `DepartmentController`/`DepartmentService` pattern (DTOs as
  records, soft-delete aware queries via existing `@SQLRestriction`).
- Machine `status` field is constrained to `OPERATIONAL`/`UNDER_MAINTENANCE`/
  `DECOMMISSIONED` at the DB level (see `enums/OperationCondition.java` and the check
  constraint in the migration) — service layer must not allow invalid transitions once
  Phase 5's event model exists; until then, validate against the enum.
- **Acceptance:** full CRUD test coverage matching existing patterns; role restrictions
  from Phase 1 applied (decide machine/spare mutation access as part of the matrix).

### Phase 4 — Repair core with idempotency
- `RepairRepository` (new), `RepairService`, `RepairController` under `/api/v1/repairs`.
- `repairs.idempotency_key` is already a unique column in the schema — the create
  endpoint must accept an idempotency key (client-supplied or derived) and return the
  existing record on a duplicate key rather than erroring or duplicating.
- Repair creation must validate `machine_id` exists, `technician_id` is optional
  (nullable in schema), and `repair_type`/`repair_priority`/`repair_status` match the
  enums (`RepairType`, `RepairPriority`, `RepairStatus`).
- **Acceptance:** duplicate idempotency-key requests return the same resource, not a
  second insert or a 500; full test coverage.

### Phase 5 — Domain events + `RepairUpdate`
- Introduce Spring application events (or a lightweight domain-event pattern) so machine
  status transitions happen as a reaction to repair lifecycle changes, not as direct
  field mutation from unrelated services — per locked decision §1.7.
- `RepairUpdate` rows are created append-only whenever a repair's status changes — never
  updated or deleted once written. Add a service method for appending an update, not a
  generic repository save exposed to callers.
- **Acceptance:** creating/progressing/completing a repair produces the expected
  `RepairUpdate` trail and machine status changes, verified via integration tests (not
  just unit tests mocking the event bus).

### Phase 6 — `RepairSpare` with pessimistic locking + full test coverage
- `RepairSpareRepository`/service: consuming spares against a repair must decrement
  `spares.stock` and write `used_quantity` on the join row atomically. Use pessimistic
  locking (`@Lock(LockModeType.PESSIMISTIC_WRITE)`) on the `Spare` row during consumption
  to prevent oversell under concurrent repairs — this is the reason the design calls out
  pessimistic (not optimistic) locking specifically for this path.
- **Acceptance:** a concurrency test (two threads/requests consuming the last unit of a
  spare) proves only one succeeds and stock never goes negative.

### Phase 7 — Hardening pass / release readiness
- Re-run the full P0 checklist against the state of the repo at this point — confirm
  nothing regressed.
- Confirm `springdoc` swagger UI (`/swagger/ui`) and `/v3/api-docs` reflect all new
  endpoints correctly, and decide whether they stay `permitAll()` in a non-local
  environment.
- Review `resilience4j-ratelimiter` — either wire it onto the auth endpoints
  (login/refresh are the obvious rate-limit targets) or remove the unused dependency.
- Full regression: `mvn verify`.

## 6. Non-Goals / Guardrails

- Do not reintroduce public self-registration.
- Do not replace soft-delete (`@SQLDelete`/`@SQLRestriction`) with hard deletes on
  history-bearing entities.
- Do not switch `ddl-auto` back to `update`/`create` once Flyway is enabled — schema
  changes go through new versioned migration files only.
- Do not add a third system role — `TECHNICIAN` stays a non-login domain entity.
- Do not commit real secrets, keys, or non-placeholder `application.properties` values.
- Do not weaken CORS beyond the two configured origins (`http://localhost`,
  `https://msi.leo-blenny.ts.net`) without an explicit reason recorded in this file.
